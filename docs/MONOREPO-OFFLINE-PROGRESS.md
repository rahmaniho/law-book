# گزارش آغاز فاز دوم — مونوریپو، sandbox و اصلاح آفلاین

تاریخ: ۲۰۲۶/۱۰/۱۰ · شاخه: `arena/8f556cd2-law-book`

## خلاصهٔ وضعیت

درخواست این مرحله: انتقال به مونوریپو در `law-book`، شروع با sandbox، رفع شکاف آفلاین و یکپارچه‌سازی workflowهای Pages.

**انتقال و اصلاح آفلاین پیاده‌سازی و آزمون شدند. sandbox در حد اسکلت امن بک‌اند آغاز شده است؛ درگاه متصل نیست. فاز دوم به‌طور کامل تمام نشده و این خروجی آمادهٔ فروش نیست.**

## ۱. انتقال بدون بازنویسی محصول

- سورس واقعی به `apps/web` وارد شد؛ منشأ دقیق در [IMPORT.md](IMPORT.md).
- `apps/api` یک workspace مستقل Fastify/TypeScript است.
- `apps/admin` صرفاً محل مستندشدهٔ پنل آینده است، نه پنل صوری و نه مسیر مخفی مدیریت.
- یک package-lock و npm workspaces در ریشه؛ اجرای scripts وب همچنان با cwd همان برنامه.
- حداقل Node نسخهٔ ۲۲٫۱۷؛ CI روی Node 22.
- منابع حقوقی `data/` و snapshot اولیهٔ `public/data` **بایت‌به‌بایت با مبدأ یکسان** نگه داشته شدند: ۴۶ سند، ۷٬۲۷۸ ماده، ۱٬۹۹۸ رأی.
- شکل ظاهری، محاسبه‌گرها، جست‌وجو، نشان‌ها و خوانندهٔ موجود بازنویسی نشده‌اند.

## ۲. رفع شکاف آفلاین

### چرا تنها افزودن کش RSC کافی نبود؟

کش زمان اجرا تنها مسیر بازشده را نگه می‌دارد. مادهٔ تازه‌ای که کاربر در حالت آفلاین باز کند همچنان پوستهٔ HTML/RSC ندارد، حتی اگر متن آن در IndexedDB باشد.

### تغییرات اجراشده

1. مسیر مشترک `/read/?article=<id>` یا `/read/?law=<id>` به مؤلفه‌های خوانندهٔ قبلی متصل شد. داده از همان IndexedDB می‌آید؛ کتابخانه یا مدل دادهٔ جایگزین ساخته نشد.
2. لینک‌های مواد، قوانین، نتایج جست‌وجو، نشان‌ها، مواد قبلی/بعدی/مرتبط و اشتراک‌گذاری به این پوسته هدایت می‌شوند. URL اشتراک‌گذاری basePath را نیز حفظ می‌کند.
3. صفحات `/article/[articleId]` و `/laws/[lawId]` حذف نشدند. لینک مستقیم قدیمی در حالت آفلاین، در صورت نبود صفحهٔ کش‌شده، به خوانندهٔ مشترک هدایت می‌شود.
4. HTML و RSC پوسته‌های ثابت جداگانه پیش‌کش می‌شوند؛ query خواننده و توکن `_rsc` کلید کش را تکثیر نمی‌کنند. پاسخ HTML هرگز جای پاسخ RSC داده نمی‌شود.
5. اسکریپت `build-precache.mjs` از خروجی واقعی build، فهرست JS/CSS/فونت‌ها/آیکون‌ها و fingerprint می‌سازد و در `out/sw.js` درج می‌کند. فایل خروجی تولیدشده وارد Git نمی‌شود.
6. نصب ناقص پوسته fail می‌شود و worker سالم قبلی را جایگزین نمی‌کند. نسخهٔ جدید اجباری روی تب قدیمی فعال نمی‌شود.
7. پاک‌سازی کش فقط به namespace همین basePath محدود است؛ داده‌های نسخه‌ای و کش برنامه‌های دیگر حذف نمی‌شوند. کش RSC زمان اجرا فقط برای مسیرهای ایستای legacy است، نه API یا هر فایل متنی دلخواه.
8. خطای HTTP اشاره‌گر نسخه، آخرین اشاره‌گر سالم را در کش خراب نمی‌کند.

**اندازهٔ اندازه‌گیری‌شدهٔ پیش‌کش پوسته: ۲٫۲۲ MiB غیرفشرده، شامل ۵۰ asset و ۲۴ منبع HTML/RSC.** دادهٔ قوانین جداگانه دریافت می‌شود؛ آراء همچنان اختیاری‌اند.

برای سازگاری لینک‌های قدیمی، خروجی کامل ایستا فعلاً حدود **۲۰۶ MB و ۷٬۳۳۹ صفحه** باقی مانده است. این مرحله ادعای کاهش کل خروجی به چند مگابایت ندارد.

### شرایط و محدودیت‌ها

- نخستین دانلود قوانین و نصب موفق SW به اینترنت نیاز دارند.
- این اصلاح وابستگی مطالعهٔ مادهٔ بازنشده به شبکه را برطرف می‌کند؛ جلوی پاک‌شدن داده به‌دست کاربر یا eviction مرورگر را نمی‌گیرد.
- RSC یک مسیر legacy بازنشده عمداً با دادهٔ ساختگی پاسخ داده نمی‌شود؛ همهٔ لینک‌های جدید برنامه از خوانندهٔ مشترک می‌روند، و لینک مستقیم قدیمی با redirect پوشش داده شده است.
- صحت حقوقی محتوا، تراکنشی‌شدن نصب بسته‌ها، hash-check دانلودها و بازیابی حساب، موضوع مراحل بعدی‌اند.

## ۳. sandbox — چه چیزی هست و چه چیزی نیست؟

### پیاده‌سازی‌شده

- Fastify با اعتبارسنجی تنظیمات و محدودیت اندازهٔ بدنه.
- `PAYMENT_MODE=sandbox` پیش‌فرض؛ مقدار `live` یا مقدار ناشناخته باعث توقف startup می‌شود.
- `GET /api/health` صریحاً `paymentMode: sandbox` و `paymentsAvailable: false` اعلام می‌کند.
- `POST /api/payments` فعلاً 503 برمی‌گرداند؛ callback تأییدکنندهٔ صوری وجود ندارد.
- فایل نمونهٔ تنظیمات فقط سمت سرور؛ بدون رمز، merchant ID یا کلید خصوصی.
- آزمون‌ها بررسی می‌کنند که ورودی جعلی «موفق» نمی‌تواند پرداخت یا مجوز ایجاد کند.

### هنوز انجام نشده

اتصال واقعی به sandbox درگاه، دیتابیس سفارش، احراز هویت، verify رسمی سمت سرور، idempotency مالی و صدور مجوز امضاشده. **هیچ پرداخت آزمایشی در شبکهٔ درگاه انجام نشده است.** پیش از افزودن مسیر خرید، این اجزا باید با هم پیاده‌سازی و تست شوند؛ صرف برگشت از درگاه هیچ اعتباری ندارد.

## ۴. workflowهای Pages

- دو workflow استقرار مبدأ با یک فایل ریشهٔ `.github/workflows/deploy.yml` جایگزین شدند.
- مسیر artifact برابر `apps/web/out` و basePath برابر `/law-book` است.
- نصب از lockfile ریشه؛ `npm run build:web` ساخت داده و precache را نیز اجرا می‌کند.
- تایپ‌چک، تست‌ها، lint و آزمون مرورگر پیش‌شرط deploy هستند.
- `ci.yml` فقط build/test انجام می‌دهد و هیچ دسترسی deploy ندارد.
- Pages فقط فایل ایستا منتشر می‌کند؛ بک‌اند و secrets به artifact وارد نمی‌شوند.
- **workflowهای مخزن قدیمی `rahmaniho/Lawbook` تغییر نکرده‌اند.** رفع رقابت استقرار در مونوریپوی جدید انجام شده؛ خاموش‌کردن استقرار قدیمی تصمیم مجزاست.
- فعال‌سازی Pages، اجرای GitHub Actions و انتشار عمومی در این نوبت انجام نشده‌اند.

## ۵. شواهد اجرایی

| بررسی | نتیجه |
| --- | --- |
| `npm ci` در ریشه | موفق |
| `npm run build` | موفق؛ ساخت وب + آماده‌سازی precache + تایپ‌چک API |
| `npm run typecheck` | موفق برای هر دو workspace |
| `npm test` | ۷۹ آزمون وب + ۳ آزمون API؛ **۸۲ موفق، صفر شکست، صفر skip** |
| `npm run lint` | بدون خطا یا هشدار |
| `npm run test:offline` | موفق در Chromium واقعی برای دسکتاپ و viewport موبایل |
| تطبیق دادهٔ واردشده با مبدأ | منابع و snapshot اولیه یکسان |
| `npm audit --omit=dev` | **۱۰ آسیب‌پذیری: ۱ بحرانی، ۶ بالا، ۳ متوسط؛ هنوز رفع نشده‌اند** |

آزمون مرورگر، بدون mock داده یا پاسخ شبکه:

1. دانلود واقعی قوانین و نصب worker در یک context تازه.
2. بستن صفحهٔ اولیه برای حذف کش درون‌حافظه‌ای Router.
3. غیرفعال‌کردن کش HTTP و قطع شبکه با Playwright.
4. بازکردن فهرست قوانین، رفتن به قانون و مادهٔ قبلاً بازنشده از لینک واقعی.
5. بررسی متن واقعی ماده و دریافت RSC از Service Worker.
6. نشان‌کردن ماده و بازگشت به آن از نشان‌ها، reload، مادهٔ بازنشدهٔ دیگر و لینک قدیمی.
7. بازکردن محاسبه‌گر و تعامل با ورودی، جست‌وجوی محلی و رفتن به نتیجه.
8. بررسی نبود خطای JavaScript در مرورگر.

این آزمون **گوشی فیزیکی Android یا Safari/iOS نیست**. در سطح SW نیز ریشهٔ دامنه، `/law-book` و `/Lawbook`، نصب ناقص، queryهای متفاوت و حفظ کش سایر برنامه‌ها آزمایش شدند.

## ۶. باقی‌مانده و ترتیب بعدی

### تصمیم‌های باز کارفرما

- چه چیزی فروخته شود: فریمیوم، همهٔ نسخهٔ جدید یا فقط به‌روزرسانی‌های آینده؟ محتوای فعلی بدون تصمیم شما پولی نشده است.
- میزبانی واقعی: VPS، PaaS یا سرور موجود؟ هیچ سرویس پولی خریداری یا انتخاب قطعی نشده است.

### کارهای فنی بعدی

1. نهایی‌سازی مدل داده و مرزهای محصول/نسخه/بسته؛ حفظ مدل مجوز مادام‌العمر.
2. رفع وابستگی‌های آسیب‌پذیر با آزمون سازگاری؛ بدون `audit fix --force` و بدون ارتقای عمدهٔ کورکورانه.
3. PostgreSQL، حساب/OTP و نشست‌ها، سفارش با snapshot قیمت، adapter رسمی sandbox و verify/idempotency سمت سرور.
4. صدور و بازیابی مجوز امضاشده، مدیریت دستگاه با محدودیت‌های شفاف آفلاین.
5. دانلود بسته با hash و نصب تراکنشی، سپس پنل مجزای دارای مجوز سمت سرور.
6. تست Android واقعی، iOS/Safari، شکست ذخیره‌سازی و سناریوی ارتقای PWA؛ تنظیم و اجرای انتشار پس از تأیید.

پیش‌نمایش این مرحله خروجی ایستای واقعی است؛ فعال‌بودن آن به معنی آماده‌بودن فروش، درگاه یا سرور تجاری نیست.
